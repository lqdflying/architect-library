# Branch strategy

Applies in every Claude Code session. One working branch at a time. The branch you are already on is that branch.

- Before the first write, run `git status --short --branch`. A session note that the directory is not a git repo does not replace that command. When the branch is `main` and no working branch exists, create the working branch before editing. Name it from branch names already used in that repository. Do not ask the user for the name. When a working branch already exists, check that branch out again, including when you were the one who checked out `main`.
- **`main` is protected against writes. Checking it out is allowed.** Never edit, commit, or push on `main`. Read-only use is fine and expected: check it out, read it, or fast-forward it (`git fetch origin main:main`). Delete a branch only when the user asks. A merged branch you are keeping is not deleted from `main`. The rule bites at the first write. If `main` is checked out and a file must change, return to the existing working branch when one exists; create a branch only when none exists, and make every edit there. Being on `main` is not permission to write, and a request to edit files while on `main` means leave `main` before the first edit.
- Any other current branch is the non-main working branch. Stay on it for the task already in progress and for the next task, whatever the topic. Do not create or check out another branch because the work is a fix, a new task, a different phase, or a different subject from the branch name.
- Do not switch away from a branch that holds unmerged commits or uncommitted files. The new branch cannot see that work, so switching strands it. Once its commits are merged into `main` and the tree is clean, keep working on it: update it with `git fetch origin` and `git merge --ff-only origin/main` before the next edit. If the fast-forward fails, stop and ask.
- A new branch is allowed when `main` is checked out and no working branch exists, or when the user explicitly asks for one. Create that branch from `main`. A `main` checkout you made yourself while a working branch existed does not count: go back to that branch instead.
- **One branch and one push may carry several unrelated topics.** A commit on a different subject (a naming fix landing on a tagging branch, a docs change landing on a feature branch) is expected. Do not propose splitting a branch, moving a commit to its own branch, or requiring one PR per topic unless the user asks for that split. The branch is a workstream, not a topic.
- Pause for user confirmation before `git commit` or `git push`.
